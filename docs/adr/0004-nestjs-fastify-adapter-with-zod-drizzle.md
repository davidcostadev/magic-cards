# ADR 0004: NestJS (Fastify adapter) for the REST API, keeping Zod + Drizzle

- **Status**: Accepted
- **Date**: 2026-05-31
- **Deciders**: David Costa
- **Reverses**: the *framework* choice of ADR 0002 (Fastify-standalone over NestJS)
- **Refines**: ADR 0003 (the REST/Stripe/OpenAPI decision stands; this fixes the transport/structure)

## Context

ADR 0002 chose **Fastify standalone over NestJS** with one load-bearing reason: tRPC made NestJS's
value proposition (controllers, pipes, interceptors, guards, DI) redundant. ADR 0003 then **removed
tRPC** in favor of a Stripe-style REST API typed via OpenAPI.

With REST back, that premise is gone — and NestJS's building blocks map almost one-to-one onto the
Stripe-style design from ADR 0003:

- a global **exception filter** → the error envelope `{ error: { type, code, param } }`
- a global **interceptor** → the list envelope `{ object: "list", data, has_more, url }`
- a **guard** → JWT auth (replacing what would have been a Fastify `preHandler` hook)
- **`@nestjs/swagger`** → the OpenAPI 3.1 spec that is the backbone of the type-safety chain

With Fastify standalone, each of those is hand-rolled. With NestJS they are first-class.

## Decision

Build the backend with **NestJS running on the Fastify adapter** (`@nestjs/platform-fastify`) — keeping
Fastify's performance under NestJS's structure. Keep **Zod as the single source of truth** via
**`nestjs-zod`** (`ZodValidationPipe` + `createZodDto` + `patchNestjsSwagger`), so validation and the
OpenAPI spec are driven by the same schemas — class-validator/class-transformer DTOs are **not** used.
Keep **Drizzle ORM** (not Prisma).

The frontend type-safety chain is unchanged from ADR 0003: backend emits `openapi.json` → frontend
generates types via `openapi-typescript` → typed `openapi-fetch` client → TanStack Query. To close the
sync gap, the spec is **committed to the repo** (generated by a standalone `gen:api` script that boots
Nest without listening) and **CI fails if the committed spec drifts** from the schemas.

## Options considered

- **Framework**: NestJS + Fastify adapter (chosen) · NestJS + Express adapter (loses Fastify perf, broader
  middleware compat) · Fastify standalone (lighter, but hand-roll filter/interceptor/guard/swagger).
- **Validation**: `nestjs-zod` (chosen — keeps Zod as source of truth) · class-validator DTOs (idiomatic
  Nest, best-documented, but abandons Zod).
- **ORM**: Drizzle (kept — SQL-close, good for the aggregation-heavy dashboard/streak queries; the swap to
  Prisma had no premise change, only preference) · Prisma (best-documented with Nest, but `$queryRaw` for
  the streak query).

## Consequences

- **Backend structure** is NestJS modules (controller + service per resource: auth, subjects, cards,
  reviews, dashboard) plus a `common/` layer: `JwtAuthGuard`, a global `HttpExceptionFilter` (error
  envelope), a global list interceptor (list envelope), and cursor/pagination helpers.
- **Services** (SM-2, auth, learning) become injectable Nest **providers** — the logic is identical and
  remains framework-agnostic; only the wiring (DI) changes.
- **More ceremony than Fastify-standalone** (decorators, modules), accepted in exchange for the
  envelope/auth/swagger ergonomics.
- **Against the grain of two project conventions**: NestJS conventionally uses Jest + ESLint/Prettier; we
  keep **Vitest + Biome** (both work with Nest, just less-trodden).
- **`nestjs-zod` is a less-trodden path** than class-validator, but preserves the single-source-of-truth
  principle carried through ADR 0003 and the OpenAPI chain.
- **ADR 0003 still holds** — REST `/v1`, Stripe envelopes, conventional verbs, JSON bodies. This ADR only
  changes *who serves it* (NestJS-on-Fastify) and *how cross-cutting concerns are implemented*
  (filter/interceptor/guard vs. hand-rolled). Two ADR-0003 details were also dropped after review:
  `expand[]` (a single first-party client joins from the TanStack Query cache) and `Idempotency-Key`
  (the frontend disables the submit button via `isPending`; double-`POST /v1/reviews` is prevented
  client-side). IDs are **UUIDv7** so list endpoints can use them directly as pagination cursors.
